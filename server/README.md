# Российский узел проверки SV IPTV

Пакет для Ubuntu 24.04: проверяет каналы с сети VPS и хранит результаты независимо
от домашнего компьютера и зарубежного GitHub Actions. Основной `main/tv.m3u`
этот пакет не изменяет. Перед использованием российской сборки для приставок
нужно сравнить первый полный отчёт с домашним и проверить подозрительные кадры.

## Установка

На сервере достаточно 2 ядер и 4 ГБ памяти для начала проверки с двумя рабочими
процессами. Это стартовая настройка, а не измеренная гарантия времени полного прохода.
Панель ispmanager не требуется. Не устанавливайте этот пакет на чужой или
уже занятый другим проектом сервер без проверки путей.

Получите каталог `server` из этой версии репозитория и выполните:

```bash
sudo bash server/install.sh
```

Установщик устанавливает Python, Git и FFmpeg из репозиториев Ubuntu, создаёт
отдельного системного пользователя `sv-iptv-ru`, службу и таймер. Он не меняет
пароль, настройки SSH, firewall или действующие плейлисты.

Первый проход запускается сразу. Затем сервер работает круглосуточно: примерно
через одну минуту после завершения прохода начинает следующий, без наложения.
После перезагрузки проверка возобновляется примерно через минуту. Телефон или
домашний компьютер для продолжения проверки не нужны.
Защитный предел одного прохода — 48 часов, чтобы длительная очередь не обрывалась
через шесть часов. Сетевые запросы и декодирование по-прежнему имеют отдельные
короткие таймауты. Результаты и история сохраняются на диске; совместимый недавний
промежуточный результат может использоваться повторно. Круглосуточные проходы
не означают непрерывного просмотра каждого канала. Расширенная очередь выполняется
порциями до 1000 запросов, с публикацией отчёта после каждой порции. Завершение
порции не считается полным проходом всех 232 674 ключей.

```bash
sudo journalctl -u sv-iptv-ru.service -f
sudo systemctl status sv-iptv-ru.service
sudo systemctl list-timers sv-iptv-ru.timer
sudo systemctl start --no-block sv-iptv-ru.service
```

## Состав проверки

Каждый запуск получает актуальный `main` только из `slawa99-prog/sv-iptv`.
Исследуется весь закреплённый архив, включая неизвестные и зарубежные названия.
Фильтр разрешённых каналов ограничивает допуск в плейлист, а не исследование
архива. Проверяются видео, звук, продвижение HLS и известные визуальные заглушки.
Неподдерживаемый формат остаётся непроверенным, а не считается мёртвым потоком.
История другого узла не импортируется.
Адреса с меткой ограничения по стране проверяются: узел находится в России.
Регион VPS сам по себе не доказывает доступность потока в домашней сети.

Рабочий каталог: `/var/lib/sv-iptv-ru/results`. В нём `status.json`, `history.json`,
`backups.json`, `tv.m3u`, `node.json`, промежуточные результаты и проблемные кадры.
`tv.m3u` здесь — результат VPS, а не основной плейлист на GitHub. Если защитные
пороги блокируют сборку, отчёт получает `publication: blocked`; M3U может остаться
от предыдущего успешного прохода. Дата M3U — `last_published_utc` в отчёте.

## Сохранение результатов в GitHub

Без отдельного ключа проверка работает, результаты остаются на сервере.
Для автоматической публикации нужен fine-grained GitHub token владельца:
только репозиторий `slawa99-prog/sv-iptv`, разрешение Contents: read and write.
Ключ вводится на сервере в `/etc/sv-iptv-ru/github-token`, владелец root, режим 0600.
Не добавляйте ключ в Git, командную строку, отчёт или переписку.
Служба получает его через systemd LoadCredential.

Код публикует только отчёты и проверенные части истории в отдельную ветку `ru-checks`
того же репозитория. История российского узла остаётся отдельной; основной
`main`, его плейлист и история не затрагиваются. При конфликте обновления
ветки принудительная запись запрещена, а локальный отчёт сохраняется.
Ограничение на ветку реализовано кодом; само разрешение Contents даёт доступ
к содержимому выбранного репозитория, а не только к этой ветке.

После настройки ключа публикация произойдёт в конце следующей завершённой порции.
Неудачный доступ к GitHub не удаляет локальные результаты. Кадры и промежуточные
результаты остаются локально; публично сохраняются завершённые отчёты и M3U.

Большая история публикуется без удаления измерений. При размере более 40 МиБ
`history.json` становится индексом `sv-iptv-history-parts-v1`; части находятся
в `history-parts/`. Берите индекс, все части, `status.json` и `node.json` из одного
коммита. Для проверки SHA256 и восстановления полной истории:

```bash
python3 server/history_parts.py /path/to/ru-checks-snapshot /path/to/history-full.json
```

На сервере файл `/var/lib/sv-iptv-ru/results/history.json` всегда остаётся полным.
Пустой `requests` в опубликованном индексе не означает нулевое число измерений.

## Обновление и остановка

Проверяющий код и каталоги обновляются перед каждой порцией из `main`.
Установленный запускатель обновляется отдельно. Для полного архива 232 674
нужна версия с `history_parts.py`; публикация в GitHub сама по себе её не устанавливает.
Возьмите точный 40-символьный SHA опубликованной версии и выполните:

```bash
revision='EXACT_40_CHARACTER_COMMIT_SHA'
curl -fsSL "https://raw.githubusercontent.com/slawa99-prog/sv-iptv/$revision/server/update.sh" -o /tmp/sv-iptv-update.sh
bash /tmp/sv-iptv-update.sh "$revision"
```

Команда выполняется от root. Сначала проверяются файлы очередей, затем
останавливаются таймер и служба, сохраняются результаты и контрольный файл
в `upgrade-backups/`, обновляется запускатель и проверка возобновляется.
При ошибке установки выполняется попытка восстановления прежнего запускателя.
Токен и накопленная история не заменяются. После запуска проверьте журнал:

```bash
journalctl -u sv-iptv-ru.service -n 30 --no-pager
```

Строка `Campaign ...: 232674 frozen requests` подтверждает загрузку очереди.
После окончания порции сверяйте `node.source_commit`, `node.frozen_queue_requests`,
`node.report_history_format` и `status.expansion_campaign`. Старый опубликованный
узел сообщает лишь о последнем опубликованном проходе, не о текущем процессе.

### Проверка формата на ru-vps

Версию проверки показывает поле `status.media_probe_version`. Для открытого live
DASH с одним периодом и явным `SegmentTimeline` проверка скачивает
видеосегменты и звук за общий интервал. Для HLS с байтовыми диапазонами сервер
источника должен вернуть точные диапазоны с HTTP 206. В обоих случаях FFmpeg
декодирует обе дорожки, проверяются кадры и появление новых медиаданных.
Для непрерывного HTTP MPEG-TS/FLV выбирается полное окно от ключевого кадра.
Допуск такого варианта по-прежнему требует просмотра прямого эфира, подтверждения
названия и языка, отсутствия заглушки и накопленной стабильности.

Ограничения декодера, страницы авторизации, шифрование и неоднозначные файлы
остаются в очереди разбора. Для незавершённых запросов со старой причиной,
которую теперь умеет разбирать проверка, предусмотрена одна досрочная попытка
после интервала минимум в два часа. При повторном неопределённом результате
действует обычный интервал 168 часов. Зачёт возможен только по новому наблюдению.

### Увеличение числа параллельных проверок

Запускатель поддерживает от 1 до 12 параллельных проверок. На VPS с 4 vCPU
можно оставить 8. После перехода на 8 vCPU и 12 ГБ RAM начните с 10 и сравните с
12 по зачтённым испытаниям в час и доле сетевых ошибок в нескольких сопоставимых
порциях. Обновление с указанным числом воркеров проверит ресурсы, сохранит
историю, контрольную точку и прежнюю настройку `90-workers.conf`, затем обновит
запускатель и перезапустит службу с выбранной настройкой. Пример для 8 vCPU.

```bash
revision='EXACT_40_CHARACTER_COMMIT_SHA'
curl -fsSL "https://raw.githubusercontent.com/slawa99-prog/sv-iptv/$revision/server/update.sh" -o /tmp/sv-iptv-update.sh &&
bash /tmp/sv-iptv-update.sh "$revision" 10
```

Для 5–8 воркеров нужны минимум 4 vCPU, для 9–12 — 8 vCPU. В обоих режимах скрипт проверяет наличие 6 ГиБ RAM. Для 9–12 он также увеличивает лимиты памяти и числа задач службы пропорционально числу воркеров.
Если ресурсы ещё не применились, команда завершится до остановки службы.
Без второго аргумента обновление сохраняет текущую настройку параллельности.
На один удалённый сервер остаётся максимум одна проверка одновременно.
Свежие совместимые результаты прерванной порции используются с прежними датами;
ещё не сохранённая последняя часть работы может проверяться повторно.
Сравните скорость нескольких завершённых порций и нагрузку через 30–60 минут.
Число процессов подтверждается `workers` следующего опубликованного `node.json`.
Изменение параллельности не сокращает длительность пробы, число независимых
наблюдений, интервалы между ними и требования допуска в основной плейлист.

Для остановки:

```bash
sudo systemctl stop sv-iptv-ru.timer sv-iptv-ru.service
sudo systemctl disable sv-iptv-ru.timer
```

Остановка службы не прекращает аренду VPS у хостера.
